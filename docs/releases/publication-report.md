# Отчёт о готовности к публикации

Дата исходной проверки: 2026-08-31. Последнее уточнение: 2026-09-16.

## Текущий итог: НЕ ГОТОВ К СТАБИЛЬНОМУ ВЫПУСКУ

### Перенос канала установки в GitHub

По решению владельца следующая версия использует GitHub Releases для установщика и пакета, публичный GHCR для контейнеров. Forgejo больше не является обязательным участником сборки, установки и итогового аудита. Старый v0.1.9 и его подписанные файлы не меняются: его образы всё ещё относятся к прежнему каналу.

Добавлены проверки анонимного скачивания всех пяти образов и stable-метаданных GitHub. VM Matrix больше не передаёт токен реестра внутрь гостевых систем. Стабильный Release использует уже испытанный pre-release без пересборки, проверяет анонимное скачивание до продвижения и возвращает прежний `latest`, если проверка нового стабильного канала не прошла.

Перед публикацией нового кандидата остаются обязательными публичность пяти пакетов GHCR, свежие CI/CodeQL/Images/VM Matrix и проверка подписанного Candidate release. Перенос сам по себе не закрывает внешние клиентские испытания. Результаты реальных прогонов и доступность нового тега фиксируются отдельно после выполнения, не заранее.

### Подготовка стабильного выпуска 16 сентября

Опубликованный v0.1.9 и его тег не изменяются. В исходниках подготовлены точечные исправления следующего кандидата:

- gRPC-Go обновлён с 1.83.1 до 1.83.2 в сборках Xray и Caddy после нового срабатывания сканера. [Описание исправления разработчиком](https://github.com/grpc/grpc-go/security/advisories/GHSA-2v4p-qf9q-27wj) относится к xDS-серверам; само присутствие библиотеки не доказывает доступность этой атаки в EzOpenPN.
- Стабильный Release теперь требует успешный VM Matrix и точное совпадение образов VM, кандидата и выбранного Images. Runs проверяются по репозиторию, пути workflow, событию, исходному SHA и результату; artifacts выбираются по неизменяемому ID, provenance привязан к попытке Images.
- Устранён цикл, при котором результаты испытаний требовалось добавить внутрь уже подписанного тега. Код остаётся под неизменяемым тегом, три файла результатов добавляются отдельным commit в `main`. Схема 2 связывает их с точной версией и SHA256 испытанного пакета.
- Release продвигает готовые подписанные файлы испытанного кандидата без повторной сборки. Перед публикацией проверяет совпадение пакета, `latest/version` и установщика стабильного канала.

Нужны новый кандидат с этими исправлениями, полные CI/Images/VM Matrix для его SHA и реальные внешние результаты. Проверки нового механизма на фикстурах не являются испытанием клиентского трафика.

На момент проверки канал статических установочных файлов отвечал HTTP 200, но Forgejo и `/v2/` реестра отвечали HTTP 502. До восстановления реестра новая установка не считается работоспособной. Переключение `latest` и стабильная публикация не выполняются.

### Подтверждённое состояние опубликованного предварительного выпуска

5 сентября владелец разрешил открыть GitHub и выпустить предварительный релиз v0.1.9. Разрешение не превращает незавершённые внешние испытания в успешные. Стабильный канал `latest` не переключается. [Актуальная карточка v0.1.9](v0.1.9.md) отделяет подтверждённую установку и CI от ещё не выполненной клиентской матрицы.

Для commit `e3067621ce7bb72330ff0aa93dda4f707ef5ecf3` прошли CI, CodeQL, Images, VM Matrix и Candidate release. Тег v0.1.9 подписан, комплект доступен в Forgejo. Пользователь самостоятельно завершил установку на VPS с 891 МиБ общей RAM без swap; Docker и Compose уже присутствовали. В предоставленном `status` все пять сервисов healthy, активных профилей 0. Это не результат испытаний клиентского трафика или отзыва профиля.

Блокеры стабильной готовности остаются: `external_evidence_missing` и отсутствующий успешный workflow `Evidence` с реальными результатами. Аудит стабильного выпуска продолжает требовать эти данные. Разрешение предварительной публикации оформлено отдельно; валидатор не ослаблен.

## Исторический отчёт до разрешения предварительной публикации

Ниже сохранены результаты прежних проверок и тогдашний план. Упоминания приватности, отсутствующих тегов и старых прогонов не описывают текущий статус v0.1.9. На момент исходного отчёта репозиторий оставался приватным; в Forgejo был доступен кандидат v0.1.7 с неподписанным Git-тегом. Этот тег не переписывается.

## Точечные исправления после аудита 5 сентября

- Операции с профилями и фоновая reconciliation сериализованы; добавлены конкурентные проверки отключения и удаления.
- Повторная установка использует транзакционное обновление с backup; ошибки preflight и pull сохраняют прежние сервисы. Проверен возврат после uninstall.
- Снимок для отката обновления создаётся после скачивания образов и остановки стека, поэтому сохраняет отзывы профилей, выполненные во время скачивания. Прерывание до переключения восстанавливает старый стек без отката базы.
- Для четырёх ОС выбраны датированные URL образов с прежними контрольными суммами. Прогон всех VM для нового commit всё ещё требуется.
- Аудит скачивает и проверяет реальный комплект Forgejo вместо требования release в приватном GitHub-зеркале.
- Каждое слово заголовка страницы входа занимает отдельную строку и не разрывается внутри; на узких экранах сохраняется читаемость без выхода за границы.

До стабильного выпуска по-прежнему нужны реальные `fixed.json`, `mobile.json`, `clients.json`, актуальные CI/Images/VM Matrix/Evidence для итогового commit и новый подписанный тег. Старый тег v0.1.7 не переписывается. Проверка подписи артефакта не заменяет проверку подписи Git-тега.

## Что уже подтверждено

- GitHub repository `A1exZabr/EzOpenPN` приватный, не является fork и использует нейтральное описание.
- Default branch называется `main`.
- Для GitHub Actions включено обязательное закрепление действий полным commit SHA.
- Default workflow permissions установлены в read-only, workflow не могут одобрять pull request review.
- Локальная история имеет один root commit.
- Исторический скан текущей зафиксированной истории проверил 1023 объекта, 74 commit и 427 blob без запрещённого текста, запрещённой типографики и очевидного секретного материала.
- CI и CodeQL прошли для последнего отправленного implementation commit до добавления этого отчёта.
- Браузерная матрица прошла 9 сценариев, включая мобильный viewport, клавиатурное управление и отсутствие serious или critical accessibility findings.
- Статические release, security, documentation и VM contract tests прошли локально.
- Репозиторий содержит ручные workflows для immutable images, четырёх чистых систем, внешнего evidence и подписанного выпуска.

## Блокирующие проверки

Исторический запуск `bash tools/publication_audit.sh` от 31 августа вернул следующие блокеры; актуальный перечень необходимо получать для итогового commit и тега:

- `external_evidence_missing`: нет реальных результатов fixed, mobile и client matrix;
- `workflow_missing:images`: финальные подписанные образы для release commit ещё не собраны;
- `workflow_missing:vm_matrix`: полный прогон Ubuntu 22.04, Ubuntu 24.04, Debian 12 и Debian 13 ещё не выполнен;
- `workflow_missing:evidence`: evidence workflow не может пройти до появления реальных результатов;
- `local_branch_not_main` и `local_remote_main_mismatch`: кандидат ещё находится в feature branch;
- `signed_release_tag_missing`: подписанный `v0.1.0` ещё не создан;
- `private_release_missing`: прежний аудит требовал release в GitHub. Теперь проверяется `published_release_verification_failed` для пользовательского канала Forgejo.

Предупреждение `branch_protection_deferred_by_private_plan` связано с ограничением текущего GitHub plan: branch protection и rulesets недоступны для этого приватного репозитория. Публичным только ради включения этой настройки репозиторий не делается. До смены видимости используются read-only workflow permissions, обязательное SHA pinning и ручные release gates. После законной смены видимости branch protection становится обязательной проверкой public-фазы аудита.

## Порядок снятия блокеров

1. Зафиксировать и отправить инструменты аудита, дождаться зелёных CI и CodeQL.
2. Перенести проверенный кандидат в `main` без переписывания истории.
3. Запустить `Images` для точного SHA, затем `VM Matrix` с artifact этого же SHA.
4. Выполнить [реальные внешние испытания](release-checklist.md), зафиксировать только sanitized JSON и запустить `Evidence`.
5. Повторить private-фазу `tools/publication_audit.sh` с доступными locked security tools.
6. После прохождения проверок исходного commit создать новый подписанный tag, выполнить ручной release workflow и проверить скачанные assets в Forgejo. Затем повторить полный audit: проверки тега и опубликованных файлов до их появления закономерно остаются блокирующими.
7. Сменить видимость отдельно, включить branch protection и повторить audit в public-фазе.
8. Проверить точную README-команду на ещё одном чистом VPS.

Ни один из отсутствующих внешних результатов не заменяется fixture, локальным handshake или зелёным CI.
