# Архитектура

EzOpenPN разделяет постоянное состояние, публичный edge и два транспорта. Контейнеры можно пересоздать без смены профилей, пока сохранены `/etc/ezopenpn` и `/var/lib/ezopenpn`.

```text
Internet
  |-- 80/tcp, 9443/tcp --> gateway --> control --> SQLite
  |-- 443/tcp ----------> xray <---- narrow gRPC
  |-- 443/udp ----------> hysteria <- internal auth
                                      control
```

## Сервисы

| Сервис | Ответственность | Публичный порт |
|---|---|---|
| `gateway` | HTTPS панели, общие ссылки, сертификат публичного IPv4 | `80/tcp`, `9443/tcp` |
| `control` | Администратор, профили, база, ссылки, runtime reconciliation | Нет |
| `xray` | VLESS + Reality поверх XHTTP | `443/tcp` |
| `hysteria` | Hysteria2 с Salamander | `443/udp` |
| `cert-sync` | Атомарный экспорт сертификата для Hysteria2 | Нет |

Сети Compose разделены на `edge` и `backend`. Управляющие интерфейсы не публикуются. Узкий supervisor Xray принимает только команду перезапуска через Unix socket и не умеет выполнять произвольные команды.

## Жизненный цикл профиля

1. `control` генерирует материалы и сохраняет зашифрованную запись в состоянии `pending`.
2. Пользователь добавляется в Xray.
3. После подтверждения профиль становится `active`, а панель показывает ссылки.
4. При отключении база первой запрещает новые входы, Hysteria2 получает kick, пользователь удаляется из Xray.
5. Xray кратко перезапускается, затем активные пользователи восстанавливаются из SQLite.
6. Фоновая reconciliation каждые 60 секунд устраняет расхождение runtime с базой.

В единственном процессе `control` создание, включение, отключение, удаление и reconciliation используют общую повторно входимую блокировку. Поэтому фоновая операция не может применить устаревший список активных профилей после успешного отзыва доступа. Не запускайте дополнительные workers или реплики `control` без межпроцессной синхронизации.

## Постоянные каталоги

| Путь | Содержимое |
|---|---|
| `/etc/ezopenpn` | Compose, конфигурация и текущий release symlink |
| `/var/lib/ezopenpn/control` | SQLite |
| `/var/lib/ezopenpn/secrets` | Мастер-ключ и серверные секреты |
| `/var/lib/ezopenpn/runtime` | Конфигурация транспортов и сгенерированные значения |
| `/var/lib/ezopenpn/caddy` | ACME account и сертификаты |
| `/var/backups/ezopenpn` | Проверенные локальные архивы |

Обновление и восстановление используют транзакционный журнал. Новый release становится текущим только после миграции и полного healthcheck. При сбое прежний symlink, image lock, база и сервисы возвращаются автоматически.

## Модель выпуска

Исходный commit определяет immutable образы и воспроизводимый bundle. Workflow стабильного выпуска запускается вручную для подписанного тега, проверяет evidence и сначала создаёт draft. Публикация стабильного релиза требует аудита истории, лицензий, артефактов и реальных сетевых испытаний. Отдельно разрешённый [предварительный v0.1.9](releases/v0.1.9.md) раскрывает незавершённые проверки и не переключает стабильный канал. Смена видимости репозитория выполняется отдельно с разрешения владельца.

GitHub используется для исходников, CI и выпусков. Пользовательский канал скачивания находится также в Forgejo: финальная проверка `tools/verify_release.sh --published TAG COMMIT_SHA` скачивает комплект без авторизации, проверяет Sigstore-подписи и совпадение версии и исходного commit. Наличие release в GitHub не заменяет доступность этого комплекта.
