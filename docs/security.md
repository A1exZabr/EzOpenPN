# Безопасность

EzOpenPN рассчитан на личный автономный сервер. Он не отправляет телеметрию, метрики, профили, адреса назначения или резервные копии во внешнюю систему проекта.

## Что сделать владельцу сервера

Публичный VPS виден автоматическим сканерам. Они ищут открытые службы, слабые пароли и уязвимости независимо от того, рассказывали ли вы кому-то об адресе. Смена стандартного порта сама по себе не защищает сервер.

1. Включите двухфакторную защиту кабинета провайдера и сохраните способ аварийного входа.
2. Настройте [SSH-ключ и отключите парольный вход](ssh-security.md). Сначала обязательно проверьте ключ в новом окне. EzOpenPN не делает этого автоматически.
3. Используйте отдельный длинный пароль панели и менеджер паролей. Не передавайте административный доступ пользователям профилей.
4. Обновляйте ОС, клиентские приложения и поддерживаемую версию EzOpenPN. Не ставьте случайные скрипты на тот же VPS. После перезагрузки проверяйте `sudo ezopenpn status`.
5. Считайте ссылку профиля и QR-код паролем. При утечке отключите и удалите профиль, затем создайте новый; повторное включение старого возвращает доступ по прежним ссылкам.
6. Храните резервную копию вне сервера в защищённом месте. Не загружайте её в issue или переписку с поддержкой.

Ключ защищает вход в SSH, но не делает сервер неуязвимым. Владелец VPS отвечает за устройство с закрытым ключом, обновления и кабинет провайдера. При подозрении на успешный взлом изолируйте сервер через провайдера и восстанавливайте чистую систему с новыми секретами. Одна смена пароля или IP не устраняет уже установленное постороннее ПО.

## Границы доверия

- Администратор входит только через HTTPS панели на `9443/tcp`.
- `gateway` публикует панель, но не имеет доступа к Docker Socket.
- `control` хранит состояние и управляет транспортами только через узкие внутренние интерфейсы.
- Xray и Hysteria2 не публикуют управляющие API наружу.
- `cert-sync` не имеет сети и только переносит сертификат в отдельный read-only volume.
- Ни один контейнер не получает `privileged`, host networking или `NET_ADMIN`.

## Локальные данные

SQLite является источником истины. Значения профилей шифруются XChaCha20-Poly1305 отдельным мастер-ключом. Поисковые значения хранятся как HMAC-SHA-256 digest и сравниваются constant-time. Пароль администратора хранится как Argon2id с 64 МиБ памяти, тремя проходами, parallelism 2, солью 16 байт и хешем 32 байта.

Сессия панели завершается после 12 часов бездействия или через 7 суток с момента входа. Сброс пароля отзывает все действующие сеансы. Изменяющие формы защищены CSRF token, cookie имеют `Secure`, `HttpOnly` и `SameSite=Strict`.

## Порты

EzOpenPN использует только `80/tcp`, `443/tcp`, `443/udp` и `9443/tcp`. SSH не перенастраивается. Если на сервере уже есть сервисы или ручная ограничивающая политика firewall, предварительная проверка останавливает установку.

## Секретные материалы

Каталог `/var/lib/ezopenpn/secrets` доступен только root. База без мастер-ключа не содержит готовых ссылок, но архив резервной копии включает оба компонента и поэтому является секретным. Не прикладывайте к отчёту:

- полные ссылки или QR-коды;
- файлы из `secrets`;
- базу и резервные архивы;
- private key сертификата;
- логин администратора или session cookie.

Команда логов удаляет известные значения, однако администратор должен просмотреть вывод перед отправкой.

## Выпуски

Bootstrap скачивает архив, checksum и Sigstore bundle, проверяет workflow identity, OIDC issuer, версию manifest и контрольную сумму до запуска. Контейнеры фиксируются полными digest. Обычный push не публикует выпуск и не меняет видимость репозитория.

CI сам по себе не доказывает работу внешних транспортов. Перед стабильным выпуском обязательны реальные передачи данных по обоим транспортам в фиксированной и мобильной сети, активный отзыв профиля и отдельная проверка клиентов. Публичный предварительный v0.1.9 разрешён владельцем проекта с явным указанием этих незавершённых проверок; это не отменяет критерии стабильного выпуска.

## Сообщение об уязвимости

Не создавайте публичный issue с техническими деталями или секретами. После публикации используйте GitHub Private vulnerability reporting в разделе Security репозитория. В сообщении достаточно версии, безопасных шагов воспроизведения и ожидаемого влияния.
