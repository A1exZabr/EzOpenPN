# EzOpenPN: проектный дизайн первой версии

Дата: 2026-08-31

Статус: утверждено пользователем 2026-08-31

## 1. Назначение

EzOpenPN превращает чистый удалённый сервер в самостоятельный узел защищённых подключений. Пользователь запускает одну команду, задаёт логин и пароль администратора, ждёт автоматическую проверку и получает ссылку на панель.

Из панели администратор создаёт профили подключения. Каждый профиль содержит два независимых транспорта:

- VLESS + Reality поверх XHTTP;
- Hysteria2 с обфускацией Salamander.

Оба транспорта относятся к одному профилю и отключаются одной операцией. Профиль рекомендуется создавать отдельно для каждого устройства, но технического запрета на повторный импорт нет.

## 2. Главный сценарий

1. Пользователь арендует чистый VPS с публичным IPv4.
2. Пользователь подключается по SSH и запускает одну команду:

   ```bash
   curl -fsSL https://github.com/A1exZabr/EzOpenPN/releases/latest/download/install.sh | sudo bash
   ```

3. Установщик проверяет сервер до внесения изменений.
4. Установщик запрашивает логин и пароль администратора через `/dev/tty`.
5. Установщик ставит Docker Engine и Compose из официального apt-репозитория, если они отсутствуют.
6. Установщик генерирует ключи, секреты и конфигурацию, затем запускает Compose.
7. Установщик получает доверенный сертификат для публичного IP и проверяет все сервисы.
8. Пользователь получает адрес вида `https://203.0.113.10:9443`, логин и команды восстановления.
9. В панели пользователь создаёт профиль, открывает краткую инструкцию и копирует ссылку или сканирует QR-код.

## 3. Публичная терминология и чистота проекта

В собственных материалах EzOpenPN используется нейтральный словарь:

- продукт: самостоятельный сервер защищённых подключений;
- сущность: профиль подключения;
- VLESS + Reality и Hysteria2: транспорты;
- пользовательские данные: ссылка подключения, QR-код, профиль;
- операции: создать, отключить, включить, удалить, скопировать.

Во всём репозитории запрещены два исторических сетевых обозначения, одно латиницей и одно кириллицей. Проверка строит эти шаблоны из кодовых точек, поэтому сами обозначения не появляются в файлах проекта.

Также запрещены:

- личные имена, контакты и идентификаторы из предшествующего проекта;
- старые домены, адреса серверов и имена сервисов;
- идентификаторы мессенджеров;
- платежная, тарифная и реферальная логика;
- сертификаты, базы и конфигурации предшествующего закрытого проекта;
- символы U+2013 и U+2014 в публичных текстах.

Репозиторий создаётся с чистой историей, не как fork. Из предшествующего проекта переносятся только проверенные поведенческие идеи. Код, документация, тестовые данные и конфигурации пишутся заново.

Первая рекомендация в README и установщике: использовать отдельный чистый VPS. Эта рекомендация показывается до команды установки.

## 4. Поддерживаемая среда

Первая версия официально поддерживает:

- Ubuntu 22.04 LTS и 24.04 LTS;
- Debian 12 и 13;
- архитектуру amd64;
- публичный IPv4, назначенный серверу;
- минимум 1 ГиБ оперативной памяти;
- минимум 4 ГиБ свободного места;
- root или рабочий sudo;
- systemd;
- доступ к GitHub, Docker Hub, Let’s Encrypt и целевым сайтам Reality.

IPv6 может оставаться включённым, но не используется как основной адрес первой версии.

Установка на сервер с существующими сайтами, панелями, сетевыми сервисами или рабочими контейнерами не поддерживается. Повторный запуск на уже установленном EzOpenPN распознаётся как обслуживание собственного экземпляра.

## 5. Предварительная проверка

До установки пакетов и изменения конфигурации bootstrap проверяет:

- поддерживаемую систему и архитектуру;
- права;
- синхронизацию времени;
- публичный IPv4;
- память и диск;
- исходящий DNS, HTTPS и доступ к реестрам образов;
- свободные `80/tcp`, `443/tcp`, `443/udp` и `9443/tcp`;
- отсутствие чужих контейнеров и конфликтующих systemd-сервисов;
- состояние host firewall;
- отсутствие ранее прерванной операции, требующей восстановления.

При конфликте установщик останавливается до опасных изменений. Сообщение содержит причину, безопасную команду диагностики и ссылку на соответствующий раздел инструкции.

## 6. Контейнерная архитектура

Compose содержит пять сервисов.

### 6.1 `control`

Назначение:

- серверная панель и JSON API;
- авторизация администратора;
- SQLite и миграции;
- создание и отзыв профилей;
- генерация ссылок и QR-кодов;
- закрытый endpoint авторизации Hysteria2;
- управление пользователями Xray через gRPC;
- сверка базы с текущим состоянием Xray.

Технологии:

- Python 3.12;
- FastAPI;
- SQLAlchemy и Alembic;
- Jinja2, небольшой vanilla JavaScript и обычный CSS;
- Argon2id для пароля администратора;
- AEAD для секретов профилей.

API документация не публикуется наружу. Контейнер слушает только внутреннюю Compose-сеть.

### 6.2 `xray`

Назначение:

- VLESS + Reality;
- XHTTP на `443/tcp`;
- закрытый HandlerService для добавления и удаления пользователей;
- узкий локальный supervisor для принудительного перезапуска только процесса Xray;
- минимальные локальные логи без адресов назначения.

Supervisor является PID 1 контейнера, принимает только команду `restart` через Unix socket с файловыми правами для `control` и не принимает путь, аргументы или произвольную команду. Docker Socket ему не доступен. Это позволяет завершить уже открытые сеансы при отзыве профиля, не выдавая панели управление контейнерами хоста. После перезапуска `control` ждёт готовности HandlerService и восстанавливает из SQLite только активных пользователей. Остальные профили могут кратковременно переподключиться.

Bootstrap генерирует:

- X25519 ключевую пару Reality;
- случайный short ID;
- случайный XHTTP path;
- ограничения fallback-трафика;
- выбранный target и допустимые server names.

Сервер принимает актуальные режимы XHTTP, а выдаваемая ссылка первой версии явно выбирает `packet-up`. Это сохраняет проверенную совместимость с разными сетями. Обычный client multiplexing поверх XHTTP не включается.

Target выбирается автоматически из небольшого нейтрального списка. Установщик проверяет кандидатов командой Xray, исключает неподходящие варианты и сохраняет только один успешно проверенный target. Смена target выполняется отдельной обслуживающей командой с резервной копией.

### 6.3 `hysteria`

Назначение:

- Hysteria2 на `443/udp`;
- Salamander с отдельным серверным секретом;
- HTTP auth через `control`;
- закрытый Traffic Stats API с отдельным случайным секретом;
- TLS с доверенным IP-сертификатом;
- нейтральная masquerade-страница.

Каждое подключение проверяет секрет профиля через закрытую сеть. В успешном ответе `control` возвращает не имя профиля, а отдельный непрозрачный идентификатор для управления активным сеансом. Если `control` недоступен, новый вход отклоняется. При отзыве `control` сначала блокирует повторную авторизацию, затем вызывает `/kick` внутреннего Traffic Stats API. Демон читает обновлённые файлы сертификата на новых TLS handshake, поэтому плановый рестарт после продления не требуется.

### 6.4 `gateway`

Назначение:

- Caddy на `80/tcp` и `9443/tcp`;
- HTTPS панели и ссылок подключения;
- автоматическое получение короткоживущего сертификата Let’s Encrypt для публичного IPv4;
- автоматическое продление;
- безопасные HTTP заголовки;
- проксирование только к `control`.

Порт 80 используется только для ACME validation и перенаправления на панель. Административный API Caddy не публикуется.

### 6.5 `cert-sync`

Назначение:

- читать хранилище сертификатов Caddy в режиме read-only;
- атомарно экспортировать текущую цепочку и ключ в отдельный volume;
- выставлять минимальные права;
- сообщать healthcheck о сроке действия сертификата.

Контейнер не имеет сети, Docker Socket и доступа к базе. Hysteria2 получает volume сертификата только для чтения.

## 7. Сети, порты и права

| Порт хоста | Протокол | Получатель | Назначение |
|---|---|---|---|
| 22 | TCP | SSH сервера | Существующий доступ, EzOpenPN не изменяет порт |
| 80 | TCP | `gateway` | ACME validation и перенаправление |
| 443 | TCP | `xray` | VLESS + Reality |
| 443 | UDP | `hysteria` | Hysteria2 |
| 9443 | TCP | `gateway` | Панель и ссылки подключения |

Compose использует две сети:

- `edge`: только сервисы, которым нужен исходящий или опубликованный трафик;
- `backend`: `control`, Xray API и Hysteria2 auth.

Traffic Stats API Hysteria2 и Unix socket supervisor не публикуются наружу. `control` может обращаться только к заранее заданным внутренним адресам управления. `gateway` удаляет входящие forwarded-заголовки и выставляет их заново из адреса TCP-соединения, а `control` доверяет таким заголовкам только от `gateway`. Поэтому rate limit и security log нельзя обойти подменой клиентского заголовка.

Требования к изоляции:

- нет `privileged`;
- нет Docker Socket;
- нет host networking;
- нет `NET_ADMIN`;
- корневая файловая система контейнеров read-only, где это возможно;
- временные каталоги через `tmpfs`;
- Linux capabilities сбрасываются и добавляются точечно только при доказанной необходимости;
- образы фиксируются по версии и digest;
- наружу публикуются только порты из таблицы.

Docker publishing настраивает перенаправление портов. Bootstrap учитывает активный UFW или firewalld и добавляет только требуемые разрешения. Облачный firewall провайдера изменить универсально невозможно, поэтому установщик показывает точный список правил и проверяет доступность там, где это возможно.

## 8. Данные и секреты

Постоянные данные хранятся вне контейнеров:

- `/etc/ezopenpn`: Compose и нечувствительная конфигурация;
- `/var/lib/ezopenpn`: SQLite, состояние и runtime-файлы;
- `/var/lib/ezopenpn/secrets`: master key и серверные секреты с правами `0600`;
- `/var/lib/ezopenpn/caddy`: ACME account и сертификаты;
- `/var/backups/ezopenpn`: локальные резервные копии с правами root.

Основные таблицы:

- `admins`: логин, Argon2id-хеш, версия сессий и даты входа;
- `profiles`: имя, состояние, зашифрованные учётные данные, timestamps;
- `profile_lookups`: HMAC digest для быстрого поиска токенов без открытого хранения;
- `system_state`: схема, версия, выбранный IP, transport metadata;
- `audit_events`: локальные административные события без секретов.

Секретные поля профилей шифруются XChaCha20-Poly1305 master key, который хранится отдельно от SQLite. Для каждого значения используется новый случайный nonce. Для поиска предъявленного токена используется HMAC-SHA-256 digest и constant-time comparison. Утечка одной SQLite не должна раскрывать готовые ссылки.

SQLite работает в WAL mode. Резервная копия создаётся через SQLite Online Backup API, после чего архив проверяется отдельным открытием базы и сверкой manifest. Архив включает master key, поэтому всегда создаётся с правами `0600`, считается секретным и никуда не отправляется автоматически.

## 9. Жизненный цикл профиля

### Создание

1. Администратор вводит имя от 1 до 64 символов.
2. `control` генерирует UUID VLESS, секрет Hysteria2 и токен ссылки.
3. Секреты шифруются, а запись получает состояние `pending`.
4. `control` добавляет пользователя в Xray через внутренний HandlerService.
5. После подтверждения запись становится `active`.
6. Панель показывает общую ссылку, отдельные ссылки и QR-коды.

Общая ссылка имеет вид `https://<public-ip>:9443/s/<opaque-token>`. Endpoint возвращает Base64 от двух UTF-8 строк, разделённых переводом строки. Первая строка содержит VLESS + Reality, вторая Hysteria2. Ответ имеет `Content-Type: text/plain`, `Cache-Control: no-store` и не содержит имени администратора. Общий QR-код кодирует эту HTTPS ссылку. Отдельные QR-коды кодируют соответствующие transport links.

Если добавление в Xray не удалось, профиль переходит в `error`, секреты не выдаются, а интерфейс предлагает безопасный повтор. Фоновая сверка пытается восстановить согласованное состояние.

### Отключение

1. Профиль немедленно становится `disabled` в базе.
2. Hysteria2 начинает отклонять новые входы и получает `/kick` для непрозрачного идентификатора профиля.
3. Пользователь удаляется из Xray через HandlerService.
4. `control` просит узкий supervisor перезапустить процесс Xray и после healthcheck возвращает через HandlerService остальных активных пользователей.
5. Операция считается успешной, только когда оба транспорта отклоняют профиль, прежние сеансы закрыты, а остальные активные профили снова присутствуют в Xray.

Перезапуск Xray кратковременно прерывает VLESS-сеансы других профилей. Клиенты обычно переподключаются автоматически. Панель сообщает об этом перед подтверждением. Это осознанный компромисс первой версии ради действительного отзыва уже используемой ссылки без Docker Socket и расширенных прав у веб-приложения.

### Включение

`control` повторно добавляет пользователя в Xray и только после подтверждения переводит профиль в `active`.

### Удаление

Удаление требует подтверждения. Сначала выполняется отзыв обоих транспортов, затем секретный материал уничтожается. В audit остаются только время, действие и безопасный идентификатор события.

Профили первой версии бессрочны. Сроки действия, квоты и автоматическое отключение не входят в первую версию.

## 10. Панель

Панель русскоязычная и адаптивная.

### Экран входа

- логин;
- пароль;
- нейтральное сообщение при ошибке;
- rate limit и растущая задержка после неудачных попыток.

### Главный экран

- статус двух транспортов и сертификата;
- список профилей;
- состояния `Активен`, `Отключён`, `Нужна проверка`;
- кнопка `Создать профиль`;
- ссылка на локальную диагностику;
- постоянное напоминание: `sudo ezopenpn admin reset-password`.

### Карточка профиля

- понятное имя;
- общая ссылка подключения и QR-код;
- отдельная ссылка VLESS + Reality и QR-код;
- отдельная ссылка Hysteria2 и QR-код;
- кнопки копирования;
- краткая пошаговая инструкция импорта;
- подсказка переключить транспорт, если один вариант нестабилен;
- подсказка отключить multiplexing для Hysteria2, если такая настройка есть в клиенте;
- включение, отключение и удаление.

Инструкция объясняет процесс в четыре шага и не требует знания протоколов. Технические детали спрятаны в раскрываемый блок.

## 11. Авторизация администратора

В первой версии существует один локальный администратор.

При установке bootstrap читает логин и пароль из `/dev/tty`. Пароль вводится дважды, не передаётся через аргументы, environment или Compose labels и не выводится в лог.

Требования:

- Argon2id с параметрами, подобранными под минимум 1 ГиБ памяти;
- Secure, HttpOnly и SameSite=Strict cookie;
- CSRF token для изменяющих запросов;
- ротация session ID после входа;
- server-side session version для мгновенного отзыва;
- rate limit входа по IP и логину;
- Content Security Policy;
- запрет frame embedding;
- одинаковый ответ для неизвестного логина и неверного пароля.

Базовые параметры Argon2id: 64 МиБ памяти, 3 прохода, parallelism 2, salt 16 байт и hash 32 байта. Параметры сохраняются внутри стандартной строки хеша и могут быть повышены при последующей успешной авторизации. Сессия действует 12 часов без активности и не более 7 суток суммарно.

Удалённая регистрация, восстановление по email и публичное создание аккаунта отсутствуют.

## 12. Команды обслуживания

Bootstrap устанавливает `/usr/local/bin/ezopenpn`.

Обязательные команды:

```text
ezopenpn status
ezopenpn doctor
ezopenpn logs [service]
ezopenpn admin reset-password
ezopenpn backup
ezopenpn restore <archive>
ezopenpn update
ezopenpn reinstall
ezopenpn uninstall
ezopenpn purge
```

### Сброс пароля

`sudo ezopenpn admin reset-password` запрашивает новый пароль дважды, меняет Argon2id-хеш и отзывает все существующие сессии. Профили и transport secrets не меняются.

### Переустановка

`sudo ezopenpn reinstall`:

1. выполняет проверку;
2. создаёт резервную копию;
3. скачивает manifest стабильного release;
4. проверяет checksums;
5. пересоздаёт только контейнеры EzOpenPN;
6. применяет миграции;
7. выполняет healthchecks;
8. при сбое возвращает прошлые image digests и базу.

Профили, master key и ссылки сохраняются.

### Обновление

`sudo ezopenpn update` использует тот же безопасный цикл, но меняет версию на новую стабильную. Автоматическое обновление приложения в первой версии отключено. Автоматически продлевается только сертификат.

### Удаление

`uninstall` останавливает сервисы и по умолчанию сохраняет данные. `purge` требует ввод полного имени продукта и отдельное подтверждение, затем удаляет данные и сообщает, что восстановление возможно только из резервной копии.

## 13. Идемпотентность и восстановление

Установщик хранит локальные checkpoints и безопасно повторяется после обрыва. Повторный запуск не генерирует новые ключи поверх существующих и не удаляет успешные данные.

Каждая изменяющая операция:

- создаёт резервную копию затрагиваемого состояния;
- пишет временные файлы в том же filesystem;
- валидирует новую конфигурацию;
- применяет через atomic rename;
- проверяет health;
- возвращает предыдущую версию при ошибке.

Если сертификат не выдан, установка не объявляется успешной. Сгенерированные секреты сохраняются с root-only правами, а пользователь получает конкретную диагностику порта 80 и provider firewall. Небезопасный сертификат не включается автоматически. Для лабораторного режима будет отдельный явно названный advanced flag.

## 14. Наблюдаемость и приватность

`ezopenpn status` показывает:

- состояние контейнеров;
- локальные и публичные healthchecks;
- срок сертификата;
- состояние Xray API;
- состояние Hysteria2 auth;
- количество активных профилей;
- установленную и доступную версии.

`ezopenpn doctor` выполняет расширенную диагностику без вывода секретов.

Правила логирования:

- нет паролей, UUID, токенов, полных ссылок и private keys;
- нет журналирования адресов назначения;
- IP входа в панель хранится только в кратком security log;
- Docker log rotation ограничивает размер и срок;
- телеметрия и внешняя аналитика отсутствуют;
- автоматическая отправка отчётов отсутствует.

## 15. Образы и цепочка поставки

- собственный образ `control` собирается GitHub Actions;
- upstream-образы фиксируются по версии и digest;
- release содержит checksums, SBOM и provenance;
- установщик скачивает только release assets;
- manifest хранит точные digests всех контейнеров;
- pull по плавающему тегу запрещён;
- downgrade требует явного флага и совместимой схемы данных.

Минимальный `install.sh`, полученный по HTTPS, создаёт временный каталог и скачивает versioned bundle. До запуска bundle проверяются checksum и release signature по зафиксированной политике издателя. Проверка checksum без проверки подписи не считается достаточной. Временный каталог очищается trap-обработчиком.

Репозиторий сначала остаётся приватным. Публичность включается только после проверки истории, секретов, терминологии, лицензий и полного release gate.

Лицензия первой версии: MIT с нейтральной строкой `EzOpenPN contributors`.

### Unit

- rollback после искусственно сломанного image или migration.

### End to end

- установка одной командой на чистые Ubuntu и Debian VM;
- вход в панель реальным браузером;
- создание профиля и импорт QR-кода;
- внешнее подключение каждым транспортом;
- проверка внешнего адреса;
- передача достаточного объёма данных для оценки реальной пропускной способности;
- отзыв доступа и проверка, что оба транспорта перестали принимать новые входы;
- отзыв во время активной передачи и проверка завершения прежних сеансов;
- автоматическое переподключение другого активного VLESS-профиля после служебного перезапуска;
- проверка, что наружу не открыты лишние порты.

Минимальная клиентская матрица перед первым release:

- текущая стабильная Hiddify Next на Android;
- текущая стабильная Happ на iOS;
- текущая стабильная v2rayN на Windows.

Документация рекомендует только версии, которые прошли импорт общей ссылки и подключение обоими транспортами. Если конкретный клиент поддерживает лишь один транспорт, это явно отмечается, и он не считается прошедшим полную матрицу.

Release нельзя одобрить только по локальному handshake. Перед публикацией обязательны замеры из минимум двух внешних сетей с разными типами доступа. Результаты фиксируются в release checklist без клиентских секретов.

### Security

- Ruff, mypy и pytest;
- ShellCheck для bootstrap и CLI;
- Bandit и pip-audit;
- Trivy для образов и файловой системы;
- gitleaks и отдельный entropy scan;
- проверка Compose на privileges, capabilities, mounts и опубликованные порты;
- проверка CSRF, session fixation, brute force и безопасных headers;
- dependency review для pull request.

## 17. Критерии готовности первой версии

Версия готова, когда одновременно выполнено следующее:

1. На каждой поддерживаемой чистой системе установка завершается одной командой.
2. Итоговое сообщение содержит рабочую HTTPS ссылку на IP, логин и команды восстановления.
3. Администратор создаёт профиль без знания сетевых протоколов.
4. Общая ссылка содержит оба транспорта и импортируется поддерживаемыми клиентами.
5. Оба транспорта проходят внешний connectivity и throughput test.
6. Отключение профиля закрывает прежние сеансы и отзывает оба транспорта не позднее чем за 10 секунд.
7. Сброс пароля не меняет профили.
8. Переустановка и обновление сохраняют профили и ссылки.
9. Rollback восстанавливает рабочую версию после искусственного сбоя.
10. Сертификат автоматически продлевается до истечения.
11. В репозитории нет секретов, старых идентификаторов и запрещённой терминологии.
12. Первый раздел README явно рекомендует отдельный чистый VPS.
13. Нет незаявленных публичных портов, внешней телеметрии и критичных security findings.

## 20. Основные риски и меры

### Провайдер блокирует входящие порты

Установщик различает локальный listener, host firewall и доступность ACME. Для provider firewall показывает точные правила и не сообщает ложный успех.

### Короткоживущий IP-сертификат не продлился

Caddy выполняет автоматическое продление, `cert-sync` проверяет freshness, а `doctor` предупреждает заранее. Release test искусственно приближает expiry и доказывает renew path.

### База и Xray разошлись

SQLite является источником истины. На старте и после каждой ошибки `control` выполняет reconciliation через HandlerService.

### Hysteria2 auth недоступен

Новые входы отклоняются. Healthcheck панели показывает деградацию. Существующие transport processes не получают запасной открытый пароль.

### Обновление сломало данные

Перед обновлением создаётся проверенная резервная копия. Migration и image digests меняются как одна операция. Неуспешный healthcheck запускает rollback.

### Формально рабочее соединение непригодно в реальной сети

Release gate требует внешний throughput test, а не только handshake или локальный healthcheck.
