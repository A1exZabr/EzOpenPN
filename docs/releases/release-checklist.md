# Проверка выпуска во внешних сетях

Этот этап выполняется только на реальном чистом сервере и реальных клиентских устройствах. Локальный healthcheck, открытый порт или успешное рукопожатие не заменяют передачу данных. Пока все три evidence-файла не проходят валидатор, нельзя публиковать стабильный выпуск или переключать стабильный канал `latest`.

Владелец проекта отдельно разрешил публичный предварительный релиз v0.1.9 с раскрытием ограничений. Это исключение для предварительной публикации исходников и уже проверенного подписанного кандидата, а не отмена критериев ниже. Результаты внешних испытаний не создаются из сообщения «всё работает» или серверного `status`.

## Что считается успешным результатом

Для фиксированной и мобильной сети отдельно нужны оба транспорта:

- три передачи не менее 100 МиБ каждая;
- подтверждение, что клиент вышел именно через проверяемый внешний сервер;
- медианная скорость не ниже 2 Мбит/с;
- ни одной остановки передачи дольше 10 секунд;
- отдельная четвёртая активная передача для проверки отзыва;
- завершение активной передачи не позднее 10 секунд после отключения профиля;
- неудачная попытка повторного соединения в течение полного окна 10 секунд;
- автоматическое восстановление другого активного профиля через транспорт A не позднее 10 секунд.

Клиентская матрица требует текущие стабильные версии:

| Приложение | Система | Что проверить |
|---|---|---|
| Hiddify Next | Android | Импорт общей ссылки, оба транспорта, отзыв |
| Happ | iOS | Импорт общей ссылки, оба транспорта, отзыв |
| v2rayN | Windows | Импорт общей ссылки, оба транспорта, отзыв |

Точную стабильную версию нужно проверить в официальном источнике в день испытания и записать в результат. Preview, beta и сборка без подтверждаемой версии полную матрицу не закрывают.

## Подготовка

1. Подготовьте подписанный неизменяемый тег кандидата и успешные CI, CodeQL, Images и VM Matrix для его исходного SHA. При ручном запуске Images и VM Matrix выбранный ref должен указывать именно на `source_commit`. VM Matrix проверяет все четыре системы и сохраняет точный манифест использованных образов.
2. Сделайте пять пакетов `ezopenpn-control`, `ezopenpn-xray`, `ezopenpn-hysteria`, `ezopenpn-cert-sync`, `ezopenpn-gateway` публичными в GHCR. Публичность репозитория не меняет публичность пакетов автоматически. Запустите Candidate release на подписанном теге с ID выбранного Images: он отдельно проверяет скачивание без сохранённого логина. Сохраните ID запуска и SHA256 его `ezopenpn-bundle.tar.gz`. Разместите проверенные шесть файлов в GitHub Release этого тега как **pre-release**, без назначения `latest`. Не пересобирайте и не заменяйте файлы опубликованного кандидата.
3. Установите этот кандидат на отдельный чистый VPS точной версионированной командой. Оба значения `EZOPENPN_EXPECTED_VERSION` и `EZOPENPN_RELEASE_BASE_URL` должны указывать на этот тег. Не используйте команду другого кандидата из старого README.
4. Убедитесь, что браузер доверяет сертификату и `sudo ezopenpn doctor` завершён без ошибки.
5. Создайте отдельный временный профиль для испытания каждого отзыва.
6. Создайте ещё один профиль для проверки автоматического восстановления транспорта A. Не отключайте его во время испытания.
7. Подготовьте фиксированную сеть и независимую мобильную сеть в предполагаемом регионе использования.

Перед началом сохраните версию кандидата, контрольную сумму его пакета и время UTC. Ссылки, QR-коды и адреса в рабочие заметки не копируйте. В каждом результате схемы 2 укажите `application_version` и один и тот же `bundle_sha256`. Новый пакет того же исходного SHA не считается автоматически испытанным.

## Прогон одной сети

Повторите весь раздел сначала для `fixed`, затем для `mobile`.

1. Импортируйте общую ссылку в выбранный клиент.
2. Выберите транспорт A и выполните три передачи. Для каждой запишите номер, объём, длительность, медианную скорость и максимальную остановку.
3. Повторите три передачи через транспорт B.
4. Перед каждой серией отдельно подтвердите на клиенте, что используется ожидаемый внешний сервер. В итоговом JSON сохраняется только `external_server_verified: true`, сам адрес не сохраняется.
5. На новом временном профиле запустите четвёртую передачу через транспорт A, отключите профиль в панели и замерьте время завершения. Попробуйте соединиться снова и наблюдайте полный интервал 10 секунд.
6. Повторите предыдущий шаг на новом временном профиле через транспорт B.
7. Проверьте, что второй активный профиль через транспорт A подключился снова автоматически не позднее 10 секунд.

Если хотя бы один замер не прошёл порог, не меняйте `passed` вручную. Исправьте причину и повторите всю серию для этого транспорта.

## Что запрещено сохранять

В evidence-файлах и commit не должно быть:

- исходного или серверного IP;
- идентификатора профиля, UUID, токена, полной ссылки или QR-кода;
- имени беспроводной сети;
- учётной записи провайдера;
- адреса или названия ресурса, через который выполнялась передача;
- произвольных заметок и дополнительных полей.

Валидатор отклоняет неизвестные поля, IP, UUID, URL, повторяющиеся JSON-ключи, неканонический формат и файлы больше 1 МиБ. Проверка ожидаемого сервера выполняется до записи результата и сохраняется только как логическое подтверждение.

## Формат и запись

Соберите черновики по строгим схемам:

- [сетевая схема](network-result.schema.json);
- [клиентская схема](client-result.schema.json).

Итоговый каталог должен содержать только `fixed.json`, `mobile.json` и `clients.json`. Записывающая команда проверяет содержание, приводит JSON к каноническому формату и отказывается перезаписывать существующий файл:

```bash
mkdir -p docs/releases/evidence
uv run python tests/release/record_network_result.py \
  --input /SAFE_PATH/fixed-draft.json \
  --output docs/releases/evidence/fixed.json \
  --network-type fixed
uv run python tests/release/record_network_result.py \
  --input /SAFE_PATH/mobile-draft.json \
  --output docs/releases/evidence/mobile.json \
  --network-type mobile
uv run python tests/release/record_network_result.py \
  --input /SAFE_PATH/clients-draft.json \
  --output docs/releases/evidence/clients.json \
  --clients
```

`/SAFE_PATH` должен быть локальным временным каталогом с правами только для оператора. После проверки удалите черновики обычным безопасным способом, принятым на рабочей системе.

## Финальная проверка

```bash
uv run pytest tests/release/test_evidence.py -q
uv run python tests/release/validate_evidence.py docs/releases/evidence
uv run python tools/content_guard.py docs/releases/evidence
git diff -- docs/releases/evidence docs/compatibility.md
```

После зелёного результата добавьте точные прошедшие версии в `docs/compatibility.md`, просмотрите diff без вывода секретов, сделайте отдельный commit результатов и отправьте его в `main`. Он должен быть потомком исходного commit кандидата. Подписанный тег не перемещайте: тестируется и выпускается один и тот же пакет.

Запустите ручной workflow `Evidence`, выбрав **тег кандидата** в поле ref:

- `source_commit`: полный исходный SHA подписанного кандидата;
- `evidence_commit`: полный SHA более позднего commit в `main` с тремя результатами;
- `candidate_run_id`: ID именно того Candidate release, пакет которого испытан.

Workflow выполняет валидатор из исходного тега, а из более позднего commit читает только три обычных JSON-файла. Он проверяет принадлежность commit ветке `main`, подпись тега, точную версию и SHA256 пакета. Только успешный artifact `release-evidence-<SOURCE_SHA>` используется дальше. Результаты от другой версии, сборки, сервера или региона не переносятся.

Если исправление меняет исходный код кандидата, создайте новый тег и повторите необходимые испытания; старый тег и его файлы не переписываются. Если Images перезапускается, запускайте весь workflow, а не отдельные jobs: подписи относятся к точной попытке сборки.

## Проверка пользовательского канала выпуска

GitHub Releases является каналом установочных файлов, публичный GHCR каналом контейнеров. Forgejo не участвует в установке. После размещения проверенного предварительного выпуска выполните `bash tools/verify_release.sh --published TAG COMMIT_SHA`, указав точный тег и полный SHA. Команда без авторизации скачивает шесть файлов, проверяет подписи, контрольные суммы и исходный commit. Ошибка любого файла блокирует выпуск. До появления стабильного релиза GitHub-адрес `releases/latest/download/install.sh` может отвечать 404: для кандидата используйте его точный тег.

После всех внешних испытаний и успешного Evidence:

1. Запустите Release на подписанном теге. Передайте `tag`, `images_run_id`, `vm_run_id`, `candidate_run_id`, `evidence_run_id` из этой серии проверок. Вручную назначать `latest` не нужно.
2. Jobs `build`, `draft` и `verify-draft` требуют успешные доверенные runs, выбирают артефакты по неизменяемым ID, сопоставляют образы кандидата и VM, проверяют evidence и анонимный доступ к GHCR. Уже опубликованный pre-release используется без замены файлов; при его отсутствии создаётся draft. Скачанные файлы побайтово сравниваются с **теми же шестью файлами кандидата**.
3. Job `publish` сначала открывает выпуск как pre-release и проверяет его скачивание без авторизации. Только после этого назначает его стабильным и `latest`. Затем `tools/verify_release.sh --stable TAG SOURCE_SHA BUNDLE_SHA256` проверяет точный пакет, стабильную версию GitHub API и побайтовое совпадение установщика по короткой ссылке. При ошибке продвижения или проверки выпуск возвращается в pre-release, прежний `latest` восстанавливается. Проверьте результат отката, если GitHub API был недоступен.
4. После успешного workflow испытайте короткую команду `latest` на отдельном чистом VPS без сохранённого входа в реестр. Это дополнительная проверка публичной ссылки после ранее выполненной установки точного кандидата. При ошибке верните выпуск в pre-release и прежний `latest`, разберите причину. Не заменяйте артефакты на месте.
5. Выполните итоговый `bash tools/publication_audit.sh --phase public --tag TAG`. Текущий `main` содержит результаты, а проверки исполняемого кода относятся к исходному SHA тега; эти SHA намеренно могут различаться.

Не назначайте `latest` и не публикуйте стабильный выпуск до завершения внешних испытаний. После ошибки продолжайте с неуспешных jobs того же Release, проверив состояние GitHub. Повторный запуск не перезаписывает существующий draft или pre-release. При необходимости изменения пакета начинайте новый кандидат.
