# Защита входа на сервер: SSH-ключ вместо пароля

Сделайте это в начале настройки отдельного VPS. Установщик EzOpenPN **сам не отключает парольный вход**: без подготовленного ключа вы могли бы потерять доступ.

Открытые адреса постоянно проверяют автоматические программы. Они перебирают имена пользователей и пароли, ищут старые службы и известные уязвимости. Неудачные попытки входа в журнале сами по себе не означают взлом. Но простой пароль делает такой перебор опасным. Ключ убирает возможность войти в SSH одним угаданным паролем; он не заменяет обновления ОС и защиту вашего компьютера.

## Сначала подготовьте путь назад

- Найдите аварийную консоль в кабинете провайдера и убедитесь, что она открывается. Узнайте, как войти в неё или запустить Rescue при потере ключа.
- Не закрывайте текущее рабочее SSH-окно до последнего шага. Новые входы проверяйте **в отдельном окне**.
- Инструкция рассчитана на отдельную чистую Ubuntu или Debian из списка EzOpenPN. На сервере с другими пользователями, корпоративной авторизацией или MFA не применяйте её без разбора действующих правил.

В командах замените `SERVER_IP` своим адресом, а `root` именем пользователя, которого выдал провайдер. При нестандартном SSH-порте добавляйте `-p НОМЕР_ПОРТА` к `ssh`.

## 1. Создайте ключ на своём компьютере

Выполняйте здесь команды **на компьютере, не внутри SSH-сессии сервера**.

На Mac или Linux:

```bash
mkdir -p "$HOME/.ssh"
ssh-keygen -t ed25519 -a 64 -f "$HOME/.ssh/ezopenpn_ed25519" -C "ezopenpn-device"
```

В Windows PowerShell:

```powershell
New-Item -ItemType Directory -Force -Path "$env:USERPROFILE/.ssh" | Out-Null
ssh-keygen -t ed25519 -a 64 -f "$env:USERPROFILE/.ssh/ezopenpn_ed25519" -C "ezopenpn-device"
```

Если появляется `Overwrite (y/n)?`, ответьте `n`: ключ с этим именем уже существует. Не перезаписывайте его. Используйте существующий ключ, если знаете его назначение и кодовую фразу, либо выберите другое имя и замените его во всех дальнейших командах.

На запрос `Enter passphrase` придумайте кодовую фразу и повторите её. Она защищает файл ключа на вашем компьютере. Это не пароль сервера: запрос кодовой фразы может появляться и после отключения парольного входа.

Появятся два файла:

| Файл | Что с ним делать |
|---|---|
| `ezopenpn_ed25519.pub` | Открытый ключ; его можно добавить на сервер |
| `ezopenpn_ed25519` | Закрытый ключ; не отправлять, не выкладывать, не загружать провайдеру |

Сохраните защищённую резервную копию закрытого ключа и кодовую фразу отдельно от публичных документов. Для другого компьютера лучше сделать отдельный ключ. В Windows нужен компонент OpenSSH Client; устанавливать OpenSSH Server на домашний компьютер для этой инструкции не требуется. [Справка Microsoft о ключах](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement).

## 2. Добавьте открытый ключ на сервер

Если добавили этот ключ через кабинет при создании VPS, переходите к шагу 3. Иначе выполните **на своём компьютере** одну команду, пока вход по паролю ещё работает.

Mac или Linux:

```bash
ssh root@SERVER_IP 'umask 077; mkdir -p .ssh && cat >> .ssh/authorized_keys && chmod 700 .ssh && chmod 600 .ssh/authorized_keys' < "$HOME/.ssh/ezopenpn_ed25519.pub"
```

Windows PowerShell:

```powershell
Get-Content "$env:USERPROFILE/.ssh/ezopenpn_ed25519.pub" | ssh root@SERVER_IP 'umask 077; mkdir -p .ssh && cat >> .ssh/authorized_keys && chmod 700 .ssh && chmod 600 .ssh/authorized_keys'
```

Введите пароль сервера. Команда дописывает только открытый ключ, не заменяя ранее добавленные ключи. Ошибки доступа или отсутствующий файл нельзя игнорировать: сначала исправьте их.

## 3. Проверьте ключ в новом окне

Оставьте прежнюю сессию открытой. В **новом окне на компьютере** выполните:

Mac или Linux:

```bash
ssh -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no -i "$HOME/.ssh/ezopenpn_ed25519" root@SERVER_IP
```

Windows PowerShell:

```powershell
ssh -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no -i "$env:USERPROFILE/.ssh/ezopenpn_ed25519" root@SERVER_IP
```

Запрос `Enter passphrase for key ...` допустим. После него должен открыться сервер. При `Permission denied (publickey)` **не переходите дальше**: ключ ещё не работает. Если входили не как `root`, проверьте также `sudo -v`: административные команды должны быть доступны.

## 4. Отключите вход по паролю

Дальнейшие команды выполняются **на сервере**, в прежней рабочей сессии. Для `root` без установленного `sudo` убирайте слово `sudo`.

Сначала посмотрите, как подключаются настройки:

```bash
sudo grep -nE '^[[:space:]]*(Include|Match|AuthenticationMethods|PasswordAuthentication|KbdInteractiveAuthentication|PubkeyAuthentication|PermitRootLogin)[[:space:]]' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/*.conf
```

В стандартном образе в начале основного файла есть `Include /etc/ssh/sshd_config.d/*.conf`. Если его нет, видны активные `Match`, дополнительные нестандартные `Include` или параметры авторизации до этого `Include`, остановитесь и попросите проверить конкретную конфигурацию. Не удаляйте чужие настройки наугад. Для OpenSSH важен порядок: обычно берётся первое значение, а `Match` может задавать исключения. [Правила OpenSSH](https://man.openbsd.org/sshd_config).

Убедитесь, что отдельного файла из этой инструкции ещё нет:

```bash
sudo ls -l /etc/ssh/sshd_config.d/00-ezopenpn-key-only.conf
```

Ожидается `No such file or directory`. Если файл есть, не перезаписывайте его: сначала выясните, не выполняли ли вы уже эти шаги. Создайте новый файл редактором:

```bash
sudo nano /etc/ssh/sshd_config.d/00-ezopenpn-key-only.conf
```

Если `nano` не установлен, поставьте его командой `sudo apt-get install -y nano`. Вставьте четыре строки:

```text
PubkeyAuthentication yes
AuthenticationMethods publickey
PasswordAuthentication no
KbdInteractiveAuthentication no
```

В nano сохраните через Ctrl+O, Enter, затем выйдите через Ctrl+X (на Mac тоже Ctrl, не Command). Основной файл и настройки провайдера остаются прежними, поэтому для отката достаточно отключить только наш файл. `PermitRootLogin` намеренно не меняется: инструкция не включает ранее запрещённый вход root.

Проверьте синтаксис:

```bash
sudo /usr/sbin/sshd -t
```

Норма: команда ничего не напечатала и вернула приглашение. При ошибке **не перезагружайте службу**. Исправьте файл или выполните откат ниже.

Затем проверьте итоговые значения:

```bash
sudo /usr/sbin/sshd -T | grep -E '^(pubkeyauthentication|authenticationmethods|passwordauthentication|kbdinteractiveauthentication) '
```

Должны быть именно `pubkeyauthentication yes`, `authenticationmethods publickey`, `passwordauthentication no`, `kbdinteractiveauthentication no`. Если значения другие, **не продолжайте**: настройка перекрывается. На нестандартной системе администратор должен дополнительно проверить применимые `Match` через `sshd -T -C` с реальным пользователем и адресом подключения. [Описание проверки](https://man.openbsd.org/sshd).

Только после успешной проверки примените настройки:

```bash
sudo /usr/sbin/sshd -t && sudo systemctl reload ssh
```

На поддерживаемых стандартных Ubuntu/Debian используется служба `ssh`. Если служба не найдена или reload завершился ошибкой, не перезагружайте весь сервер: оставьте рабочее окно открытым и проверьте образ с провайдером. [Инструкция Ubuntu по OpenSSH](https://ubuntu.com/server/docs/how-to/security/openssh-server/).

## 5. Проверьте результат и только потом закрывайте окна

Снова в **новом окне компьютера** выполните команду входа по ключу из шага 3. Вход должен работать. Затем в ещё одном окне попробуйте вход без ключа:

```bash
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password,keyboard-interactive root@SERVER_IP
```

Ожидается отказ `Permission denied`, без возможности войти паролем сервера. Если пароль принимается или предлагается парольная авторизация, проверка не пройдена. Старую рабочую сессию пока не закрывайте.

Когда оба результата верны, SSH доступен только по ключу для проверенного пользователя. Пароль панели EzOpenPN продолжает работать в браузере. Пароль локального пользователя не удалён: он может понадобиться для `sudo` и аварийной консоли.

### Откат, если возникла проблема

В оставленной рабочей сессии **на сервере** отключите только созданный здесь файл (не удаляйте весь каталог):

```bash
sudo mv -n /etc/ssh/sshd_config.d/00-ezopenpn-key-only.conf /etc/ssh/sshd_config.d/00-ezopenpn-key-only.conf.disabled
sudo /usr/sbin/sshd -t && sudo systemctl reload ssh
```

Если файл `.disabled` уже существует, `mv -n` его не заменит: проверьте, что исходный `.conf` действительно перемещён, прежде чем перезагружать службу. Откат возвращает прежние правила, но не включает пароль, если провайдер запрещал его изначально. После потери всех сессий используйте аварийную консоль или Rescue провайдера.

## Если SSH пишет, что ключ сервера изменился

Сообщение `REMOTE HOST IDENTIFICATION HAS CHANGED` бывает после переустановки ОС или выдачи прежнего IP другому серверу, но может означать и подмену. Не отключайте проверку и не очищайте весь `known_hosts`.

Через независимую аварийную консоль провайдера на сервере узнайте отпечаток ED25519:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Если SSH показал другой тип ключа, сверяйте соответствующий открытый host-key. Для первого входа проверка такая же. Только после совпадения отпечатка и подтверждения ожидаемой переустановки удалите старую запись **на своём компьютере**:

```bash
ssh-keygen -R SERVER_IP
```

Для нестандартного порта запись выглядит так: `ssh-keygen -R '[SERVER_IP]:НОМЕР_ПОРТА'`. Подключитесь снова и ещё раз сравните отпечаток. Команда удаляет только запомненный ключ указанного адреса, а не ваш личный SSH-ключ.
