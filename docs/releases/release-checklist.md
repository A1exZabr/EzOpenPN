# Проверка выпуска во внешних сетях

Этот этап выполняется только на реальном чистом сервере и реальных клиентских устройствах. Локальный healthcheck, открытый порт или успешное рукопожатие не заменяют передачу данных. Пока все три evidence-файла не проходят валидатор, нельзя публиковать стабильный выпуск или переключать стабильный канал `latest`.

Владелец проекта отдельно разрешил публичный предварительный релиз v0.1.9 с раскрытием ограничений. Это исключение для предварительной публикации исходников и уже проверенного подписанного кандидата, а не отмена критериев ниже. Результаты внешних испытаний не создаются из сообщения «всё работает» или серверного `status`.

## Что считается успешным результатом

Для фиксированной и мобильной сети отдельно нужны оба транспорта:

- три передачи не менее 100 МиБ каждая;
- подтверждение, что клиент вышел именно через проверяемый внешний сервер;
- медианная скорость не ниже 2 Мбит/с;
- ни одной остановки передачи дольше 10 секунд;
- отдельная четвёртая активная передача для проверки отзыва;
- завершение активной передачи не позднее 10 секунд после отключения профиля;
- неудачная попытка повторного соединения в течение полного окна 10 секунд;
- автоматическое восстановление другого активного профиля через транспорт A не позднее 10 секунд.

Клиентская матрица требует текущие стабильные версии:

| Приложение | Система | Что проверить |
|---|---|---|
| Hiddify Next | Android | Импорт общей ссылки, оба транспорта, отзыв |
| Happ | iOS | Импорт общей ссылки, оба транспорта, отзыв |
| v2rayN | Windows | Импорт общей ссылки, оба транспорта, отзыв |

Точную стабильную версию нужно проверить в официальном источнике в день испытания и записать в результат. Preview, beta и сборка без подтверждаемой версии полную матрицу не закрывают.

## Подготовка

1. Установите release candidate на отдельный чистый VPS точной командой из README.
2. Убедитесь, что браузер доверяет сертификату и `sudo ezopenpn doctor` завершён без ошибки.
3. Создайте отдельный временный профиль для испытания каждого отзыва.
4. Создайте ещё один профиль для проверки автоматического восстановления транспорта A. Не отключайте его во время испытания.
5. Подготовьте фиксированную сеть и независимую мобильную сеть в предполагаемом регионе использования.

Перед началом сохраните только версию кандидата и время UTC. Ссылки, QR-коды и адреса в рабочие заметки не копируйте.

## Прогон одной сети

Повторите весь раздел сначала для `fixed`, затем для `mobile`.

1. Импортируйте общую ссылку в выбранный клиент.
2. Выберите транспорт A и выполните три передачи. Для каждой запишите номер, объём, длительность, медианную скорость и максимальную остановку.
3. Повторите три передачи через транспорт B.
4. Перед каждой серией отдельно подтвердите на клиенте, что используется ожидаемый внешний сервер. В итоговом JSON сохраняется только `external_server_verified: true`, сам адрес не сохраняется.
5. На новом временном профиле запустите четвёртую передачу через транспорт A, отключите профиль в панели и замерьте время завершения. Попробуйте соединиться снова и наблюдайте полный интервал 10 секунд.
6. Повторите предыдущий шаг на новом временном профиле через транспорт B.
7. Проверьте, что второй активный профиль через транспорт A подключился снова автоматически не позднее 10 секунд.

Если хотя бы один замер не прошёл порог, не меняйте `passed` вручную. Исправьте причину и повторите всю серию для этого транспорта.

## Что запрещено сохранять

В evidence-файлах и commit не должно быть:

- исходного или серверного IP;
- идентификатора профиля, UUID, токена, полной ссылки или QR-кода;
- имени беспроводной сети;
- учётной записи провайдера;
- адреса или названия ресурса, через который выполнялась передача;
- произвольных заметок и дополнительных полей.

Валидатор отклоняет неизвестные поля, IP, UUID, URL, повторяющиеся JSON-ключи, неканонический формат и файлы больше 1 МиБ. Проверка ожидаемого сервера выполняется до записи результата и сохраняется только как логическое подтверждение.

## Формат и запись

Соберите черновики по строгим схемам:

- [сетевая схема](network-result.schema.json);
- [клиентская схема](client-result.schema.json).

Итоговый каталог должен содержать только `fixed.json`, `mobile.json` и `clients.json`. Записывающая команда проверяет содержание, приводит JSON к каноническому формату и отказывается перезаписывать существующий файл:

```bash
mkdir -p docs/releases/evidence
uv run python tests/release/record_network_result.py \
  --input /SAFE_PATH/fixed-draft.json \
  --output docs/releases/evidence/fixed.json \
  --network-type fixed
uv run python tests/release/record_network_result.py \
  --input /SAFE_PATH/mobile-draft.json \
  --output docs/releases/evidence/mobile.json \
  --network-type mobile
uv run python tests/release/record_network_result.py \
  --input /SAFE_PATH/clients-draft.json \
  --output docs/releases/evidence/clients.json \
  --clients
```

`/SAFE_PATH` должен быть локальным временным каталогом с правами только для оператора. После проверки удалите черновики обычным безопасным способом, принятым на рабочей системе.

## Финальная проверка

```bash
uv run pytest tests/release/test_evidence.py -q
uv run python tests/release/validate_evidence.py docs/releases/evidence
uv run python tools/content_guard.py docs/releases/evidence
git diff -- docs/releases/evidence docs/compatibility.md
```

После зелёного результата добавьте точные прошедшие версии в `docs/compatibility.md`, просмотрите diff без вывода секретов и сделайте commit. Запустите ручной workflow `Evidence` для SHA этого commit. Только успешный artifact `release-evidence-<SHA>` от того же commit можно передать в ручной workflow выпуска.

Подписанный release tag должен указывать на commit с этими evidence-файлами. Повторно использовать результаты от другого сервера, версии или региона нельзя.

## Проверка пользовательского канала выпуска

GitHub используется для исходников, CI и выпусков; Forgejo остаётся отдельным каналом установочных файлов и контейнеров. После ручного размещения проверенных артефактов в Forgejo выполните `bash tools/verify_release.sh --published TAG COMMIT_SHA`, указав точный тег и полный SHA выпуска. Команда без авторизации скачивает шесть файлов, проверяет подписи, контрольные суммы и исходный commit. Ошибка любого файла блокирует выпуск.

Затем проверьте, что `latest/version` указывает на этот тег, а `latest/download/install.sh` совпадает с проверенным установщиком. Команду из README нужно испытать на отдельном чистом VPS без сохранённого входа в реестр контейнеров. Не переключайте `latest` и не публикуйте стабильный выпуск до завершения внешних испытаний.
